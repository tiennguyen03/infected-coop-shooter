# PR #16: Economy: missions pay merits; the record holds tabs

- Author: tiennguyen03 (branch `claude/economy-merits-tabs`)
- Head commit reviewed: `bcc8b9a1eabe20fe873b7db4e1c00710e389858f`
- Reviewed: 2026-11-11 (by reading the code; the tests were not run here)

**Verdict: Fix first** (no cheat found, but two ways a player's saved merits and kit can be lost).

## What it does

When a mission ends, the match server adds merits (win 120, partial 60, loss 0) to each
player's saved record and shows "+N MERITS" on the results screen. The saved record gets a
new shape ("version 2") that also holds tabs (the paid currency) and a list of paid receipts;
nothing is sold for tabs yet.

Words used below: the **DataStore** is Roblox's saved-data service. `SetAsync` writes a value
blindly over whatever is stored; `UpdateAsync` reads the stored value and changes it in one
safe step.

## Findings

1. **Publishing the match before the lobby can wipe a player's record.**
   `src/server/MeritService.luau:66-67` saves the record as version 2 the first time a mission
   pays. The lobby code on `main` today only accepts version 1
   (`main: src/shared/Rules/Record.luau:82`, `if saved.version ~= Record.VERSION ... return
   Record.new(startMerits)`): it treats a version 2 save as a brand-new soldier (1000 merits,
   no kit), and the next purchase writes that over the real record.
   Trigger: publish the match place first, or publish both but leave an old lobby server
   running. A player wins a mission, lands in the old lobby, buys anything: earned merits and
   all bought kit are gone.
   How sure: verified by reading both versions.
   Smallest fix: no code. Publish the **lobby first**, then the match, then use "Restart
   servers for updates" on the lobby. Write that order into `docs/LOBBY_MATCH_HANDOFF.md`
   (Merits) and `docs/STUDIO_MCP.md` (Places and publishing). The new lobby reads old saves
   correctly (`Record.luau:179-189`), so lobby-first is safe.

2. **A purchase in the lobby can erase merits that were just earned.** (Nova's files)
   `src/lobby/server/SaveSlot.luau:114-117` saves with `SetAsync`, and
   `src/lobby/server/RecordService.luau:95-109` (`buy`) saves the copy the lobby read when the
   player joined. The match waits at most 6 s for the pay to be saved before flying the squad
   home (`MeritService.luau:124-128`, `Config.Merits.SettleSeconds = 6`), but one pay can take
   longer (3 tries, 1 s apart, plus Roblox's own queueing when the DataStore is busy).
   Trigger: the DataStore is slow at mission end; the lobby reads the record before the pay
   lands; the player buys a gun; the lobby writes "old balance minus price" over the paid
   record. The results screen said "+120 MERITS" and they are gone.
   How sure: possible (the code path is verified; it needs a slow DataStore call to happen).
   Smallest fix: make `buy` use the `SaveSlot.update` (`UpdateAsync`) that this PR already
   adds for receipts, so the purchase is applied to what is stored, not to the lobby's copy.
   Also correct the comment at `MeritService.luau:7-8` ("the two servers never write the same
   record at once"): true for the player, not for the writes.

3. **A retried save can pay twice.** `src/server/MeritService.luau:55-84`. If a save reaches
   Roblox but the answer times out, the code tries again and adds the merits a second time.
   How sure: possible, and rare. Cost: an occasional extra 120 merits. Fine to leave for now;
   the proper fix is to stamp each pay with an id and skip it if the record already has it
   (the tabs receipts already work this way).

4. **Decision for the owner: when the record cannot be loaded, the player still gets 1000
   merits to spend for that visit.** (Nova's files) `src/lobby/server/RecordService.luau:73-84`
   and `buy` (no check of `unread`). Nothing is saved, so it is a one-visit freebie during a
   Roblox outage, and a comment says it is intended. A stricter choice is to refuse purchases
   until the record loads.

5. Small (Nova's files): the lobby's `load` treats a save it cannot understand (junk, or a
   future version 3) as a new record and the next purchase overwrites it. The match already
   refuses to touch such a save (`Record.canUpdate`). One-line fix in `load`:
   `if not answered or not Record.canUpdate(data) then unread[player] = true end`.

Checked and fine:
- No new way for a player's machine to talk to the server. A client cannot send merits, tabs
  or receipts; prices come from the server.
- A mission cannot pay twice from the run ending twice (`RunManager.endRun` returns if the
  run has already ended), and nothing pays on joining or returning to the lobby.
- Old version 1 saves load with their merits and kit and 0 tabs.
- Robux receipts are only confirmed after the tabs are saved, and a repeated receipt is
  detected on the stored record.
- The "load failed, then a save overwrites the real record" problem is fixed by this PR
  (`unread`).

## Check in Studio

1. Studio with API access off: end a run. Expect one warning and "MERITS NOT SAVED" in red;
   the run end and READY must still work.
2. API access on: wipe after the hold objective (partial). Expect "+60 MERITS"; play again
   and confirm each run adds once.
3. Wipe before the objective (loss): the screen says "+0 MERITS". Is that the text you want?
4. Published places, with an account that bought kit before this PR: win a mission, fly home,
   check old merits + 120, all kit still there, "0 TABS"; buy something, rejoin, check it stuck.
