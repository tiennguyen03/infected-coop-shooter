# PR #80: Kit Mods at the Loadmaster: ranked merit-bought soldier buffs (needs Tien's call)

- Author: MatthewDuke04 (Nova) (branch `nova/loadmaster-kit-mods`)

- Reviewed: 2026-11-18 (by reading the code; the tests were not run here)

**Verdict: Needs a decision** (it goes against two of your written rules; the code itself is
sound, with a few small fixes).

## What it does

At the Loadmaster you can spend merits on ranked "Kit Mods": permanent buffs for your soldier,
such as carrying more stims (2 → up to 5) or more stamina for sprinting and rolling (100 → up
to 160). Two more mods are shown greyed out. The match reads your ranks from your saved
record when you join.

## Findings

1. **Your call: it breaks two rules in `docs/OWNER.md`.** Line 32: "Power is the loadout,
   never stat items." Lines 56-57: merits buy "permanent unlocks (new options, never stronger
   versions)". Kit Mods are permanent stronger versions of the soldier. The PR says so itself
   and adds it to the backlog as a question for you. In co-op, a veteran with 5 stims and 160
   stamina next to a new player with 2 and 100 is a lasting gap. It is not pay-to-win: it only
   spends merits, never Robux tabs (checked). Decide yes, no, or "yes but change the rule".
2. **One failed read at join loses your bought ranks for the whole match** (sure by reading).
   The match reads your ranks once (`src/server/KitModService.luau:32` →
   `MeritService.readRecord`, which is "one try", `src/server/MeritService.luau:57-74`). If that
   read fails (four players joining at once, a save-service hiccup), you play with no extra stims
   or stamina and no warning. Fix: retry the way merit payment already does, and `warn` on the
   last failure.
3. Possible: any client can send buy requests that are sure to be refused, over and over, and
   each one still reaches the save service before being checked
   (`src/lobby/server/KitModService.luau:38-55` → `RecordService.change`). Only one is in flight
   per player at a time, but a looping hacked client could use up the lobby server's save
   budget and slow other players' buys. (The old gun buy already had this.) Fix: check the
   rank rules against the cached record first, and only go to the save service if it could pass.
4. Docs out of date: comments and docs still describe the old save path (`KitModRules.luau:8-9`,
   `MeritService.luau:8`, `docs/LOBBY_MATCH_HANDOFF.md:110`, PROGRESSION "Kit Mods"); the
   resupply text still says "Your 2 stims are refilled" for a soldier who carries 5
   (`src/shared/UpgradeDefinitions.luau:42, 52`).
5. Small: the ability bar re-reads and re-parses the ranks 15 times a second
   (`AbilityUI.luau:327`); cache it like `SprintController` does. The panel can say "Signed to
   your record." a moment early (`KitModsTab.luau` around 211-216). The dev button cannot lower
   stims.
6. Design note: there are no refunds. Lowering a mod's max rank or removing it later leaves the
   spent merits gone. Worth stating a policy if you approve the feature.

Fine: the buy uses the safe save path (a merit payment that lands during a buy is kept, an
unreadable save is left alone); old saves read as rank 0; you can only buy the next rank, never
past the max or a disabled mod; the match reads ranks from the saved record, not from data a
client could fake, and the attribute is set only by the server; the dev "SetKitRanks" button is
Studio/creator only; bots keep the normal stim count; strings and tuning are where the project
rules want them, and the new rule has tests.
