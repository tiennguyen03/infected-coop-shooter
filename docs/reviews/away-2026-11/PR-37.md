## What it does

Each mission now draws one main objective out of five (hold the site, burn the tents,
recover a record, confirm casualties, and so on) and two side objectives out of four, at
random on the server. Finishing the main one pays the reward, drops the upgrade crate and
calls the Warden; the HUD shows the list, a briefing card and markers in the world.

## Findings

1. **Possible: on this branch alone, the objective key E also uses a stim.** Objective
   prompts use E (`src/shared/Config.luau:1028`, comment: "becomes Config.Keys.Interact once
   claude/keybinds merges"; `src/server/Objectives/Kit.luau:103`), and E is still the stim
   key here (`src/client/AbilityController.luau:302-303`). A hurt player who holds E on a
   fuel can or radio likely spends a stim each time. The docs disagree with each other:
   the handoff note and `docs/MULTIPLAYER_READINESS.md:42` say F, `docs/PROGRESSION.md` and
   the HUD say E.
   How sure: both bindings verified; whether both fire on one press needs a playtest. (Same
   problem as PR-36 finding 2.) Fix: merge #40 first, or use F until then, and make the docs
   agree.

2. **Possible: "Secure the Site" might never count anyone as inside its zone, which would
   block the mission.** The new zone part has all three physics switches turned off
   (`Kit.luau:45-47`: `CanCollide`, `CanQuery`, `CanTouch` all false; used by `Kit.zone`,
   `:120-131`), and the objective asks Roblox "which parts are inside this part"
   (`Squad.zoneCount`, `GetPartsInPart`). The two zones that are known to work on `main`
   (the old hold zone and the extraction pad) leave `CanTouch` on. Whether Roblox still
   answers for a part with all three off was not confirmed.
   Trigger: dev command `SetMainObjective secure_site`, stand in the zone, watch whether
   "0 of 45s" moves. How sure: possible. Smallest fix: `part.CanTouch = true` in `Kit.zone`.

3. **An error while an objective is being set up freezes the mission.** Only the per-frame
   `step` of an objective is protected against errors
   (`src/server/ObjectiveService.luau:465`). Building it (`:282`, `module.new`) and starting
   it (`:325`, `objective.begin()`) are not. And the objectives are drawn
   (`src/server/RunManager.luau:88`) before the timer that moves the mission out of its
   landing phase is started (`:89`), so an error there leaves the squad in "Insert" forever.
   No actual error was found by reading, but none of the nine objectives has ever been run.
   How sure: the missing protection is verified; a real failure is only possible.
   Smallest fix: start the timer before `ObjectiveService.brief(...)`, and wrap `module.new`
   and `objective.begin()` in `pcall`, counting a broken main objective as done (as `step`
   already does).

4. **Objective prompts only check that the player is alive, not that they are near.**
   `Kit.luau:109-114`. The revive prompt on `main` re-checks the distance on the server
   (`Squad.luau`, "<= ReviveRadius + 2"); these do not. A cheating client that triggers
   prompts from anywhere could burn all three tents or grab the record from across the map.
   They also still work while the game is paused or after the mission has ended.
   How sure: verified by reading. Smallest fix in `Kit.prompt`: also require the player's
   body to be within the prompt's distance plus a little, and the game not paused.

5. Small: if the whole squad dies in the 4.5 s after the main objective is finished, the
   mission is reported home as "primary not done", although the reward was paid
   (`ObjectiveService.luau:237-244` waits `RadioGap` 4.5 s; `RunManager.luau:334-338` then
   returns before setting `primaryDone`). This affects merits in #16. Fix: set
   `primaryDone = true` before the "Ended" check.

6. Possible, small: in "Recover the Record", if the carrier falls out of the world, the
   record is put back at the fall position (below the map) every frame and can never be
   picked up (`src/server/Objectives/RecoverRecord.luau:133-135, 144`). Only matters if a
   player can fall through the map. Fix: put it back where it first lay.

7. Small, dev tools: force-completing "Recover the Record" while someone carries it leaves
   them unable to sprint until the next run; the dev "verify cleanup" check no longer finds
   leftover objective parts (`DevTestService.luau:177, 280`).

Checked and fine:
- The draw is made on the server, is the same for everyone, avoids repeating the last main
  objective, and copes with an empty list.
- Every main objective leads to the Warden and drops #15's reward crate; side objectives can
  fail without blocking anything.
- Hunt objectives count every death (call-ins included); their targets only appear when the
  objective starts, so they cannot be killed early.
- A record carrier who is downed, dies or disconnects drops the record where they were.
- A run restart removes every objective's parts, lights, sirens and the "carrying" state;
  delayed radio lines and the Warden call from the old run are ignored.
- Co-op: progress is shared by the squad; bots count for zones and holds; a player who
  joins late is sent the current list.
- Per-objective values are on each objective's own row; message names go through
  `Messages`; the rules have two test files.
- The lobby can ask for a particular main objective, and the match only accepts one that
  this map really offers.
- The small edits to `SprintController` (no sprint while carrying) and `EnemyService`
  (spawn helpers, quieter spawns after "Silence the Alarm") do not change normal play.
