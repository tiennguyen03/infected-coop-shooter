## What it does

When you throw a grenade, a call-in marker or the supply flare, the server now waits 0.5 s
so the thing leaves your hand at the right moment of the throw animation. The grenade,
charge or supply points are only used up at that moment, and a ball is drawn flying from
the hand to the mark.

## Findings

No crash, no way to throw for free and no way to spend twice was found. What is left is
small.

1. **During the 20 s flare cooldown, the flare key plays the throw animation and nothing is
   thrown.** `src/client/AbilityController.luau:301-307` checks the supply pool and whether
   a pallet is on its way, but the server also has a cooldown
   (`src/server/RequisitionService.luau:292`, `os.clock() >= flareReadyAt`; `Config.luau:814`,
   `FlareCooldown = 20`) that is never sent to the player's machine (`:90-97`). The empty
   throw also blocks a real grenade or call-in throw for 0.65 s.
   Trigger: throw a flare, let the pallet land, press the flare key again within 20 s with
   enough supply points. How sure: verified by reading.
   Smallest fix: publish the cooldown as a workspace attribute and add it to the client check.

2. **A second grenade thrown 0.65 to 0.8 s after the first plays the animation and throws
   nothing.** The client allows a new throw after 0.65 s (`AbilityController.luau:115-124`);
   the server wants 0.8 s between grenades (`src/server/KitService.luau:219`,
   `Config.luau:531`, `ThrowGap = 0.8`). How sure: verified by reading (this gap existed
   before; the PR makes it smaller but does not close it).
   Smallest fix: on the client, lock grenade throws for at least `ThrowGap`.

3. Small: pausing during the 0.5 s wind-up makes the animation and the throw go out of step
   (`src/server/ThrowWindUp.luau:47`). Looks odd, nothing is lost.

4. Possible: the first throw after spawning may start at the wrong point of the animation
   (`src/client/AnimationController.luau:390-393` sets the clip's start time right after
   playing it, which may be ignored while the clip is still loading). Needs a look in Studio.

5. Possible: the flare may flash on the ground mark for one frame before it "lands"
   (`RequisitionService.luau`, `buildFlare` then `flare.Parent = nil`).

6. Docs: `handoff/README.md:24` on this branch says "flare on X", but the code still uses
   key 5 (`AbilityController.luau:335`). X only arrives with #40. Wrong if #25 merges first.

7. Not from this PR, small: `src/shared/ThrowUtil.luau:19-25` accepts any aim point a
   player's machine sends. A point with an infinite value could produce a broken landing
   position (a cheater-only nuisance; possible, not tested). A one-line check that the point
   is a normal number would cover every thrown item.

Checked and fine:
- The charge, grenade or supply points are checked when you press and again at the release,
  and only spent at the release, so nothing needs refunding.
- One wind-up per player at a time: spamming the key does not throw twice.
- If you are downed, knocked over, dead or gone at the release moment, nothing is thrown
  and nothing is spent. A run restart cancels a wind-up in progress.
- Two players throwing the flare at once: one flare, one payment.
- The new message `Thrown` only goes from server to players, and the player's machine checks
  what it receives.
- Timing values are per animation in `Config`, the rule is pure with a test file.
